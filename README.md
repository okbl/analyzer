# Платежи после сделки

Инструмент для проверки сделок должников: загружаете кредитный отчёт ОКБ
(«Кредистория») в PDF, указываете дату сделки — получаете сумму и полный
перечень платежей, внесённых после этой даты, с разбивкой по кредиторам и
договорам.

## Как пользоваться

Открыть `dist/Платежи после сделки.html` двойным кликом. Всё.

Файл самодостаточный: pdf.js и парсер встроены внутрь. Ни сервера, ни
интернета не требуется. **PDF никуда не отправляется** — отчёт разбирается
в браузере на вашем компьютере, поэтому паспортные данные и ФИО должника
не покидают устройство.

Файл можно скопировать на флешку, переслать коллеге, положить на рабочий
стол — он останется работоспособным.

## Что показывает

* **Сумма и количество платежей после даты сделки** — с группировкой по
  кредиторам, внутри — по договорам, внутри — построчный список платежей
  с разбивкой на основной долг, проценты и пени.
* **График по месяцам** за всю историю: видно контраст «до сделки / после».
* **Договоры, заключённые после сделки** — по полю «Дата совершения сделки».
* **Договоры без данных о платежах** — важный раздел: по ним кредитор не
  передал в бюро построчный список, и отсутствие платежей там ничего не
  доказывает.
* **Проверка разбора** — сверка с контрольными суммами самого отчёта.

Фильтры: строго после даты сделки или включая её; верхняя граница периода;
действующие/закрытые договоры; скрытие нулевых платежей и порог минимальной
суммы (отсекает копеечные технические списания).

Отдельно — **«Не считать договоры, заключённые после сделки»**: кредиты,
взятые уже после, к прежним обязательствам не относятся. Договор считается
новым по полю «Дата совершения сделки»; договоры без даты остаются в расчёте.
Отсечённая сумма показывается явно, а не пропадает молча.

## Перекрёстная проверка по задолженности

Раздел «Сведения о сумме задолженности» — история снимков долга с датами.
Сумма снижений основного долга между снимками даёт независимую оценку того,
сколько долга погашено: она не опирается ни на таблицу платежей, ни на
агрегат отчёта.

Оценка проверена: по договору с СОВКОМБАНКом она дала 91 151,35 ₽ — ровно
столько, сколько сам отчёт указывает в поле «По основному долгу».

Главная польза — договоры, по которым построчного списка платежей нет вовсе.
В отчёте на 106 страниц таких десять, и для четырёх из них история долга
показывает погашение (89 788 ₽, 71 430 ₽, 101 138 ₽, 3 308 ₽) там, где раньше
не было видно ничего.

Это **оценка снизу и косвенная**: она не включает платежи по процентам и
пеням, а снижение долга бывает вызвано не платежом, а списанием,
переуступкой или реструктуризацией. Поэтому в расчёт она не входит — только
показывается как повод запросить первичные документы.

Можно задать несколько дат сделок — появится сводная таблица для сравнения.

Кнопка «Печать / PDF» печатает развёрнутый отчёт по всем разделам сразу,
без интерфейсных элементов — пригодно для приложения к заключению.

## Ввод даты

Поле принимает `13.12.2021`, `13122021` (точки подставляются сами),
`2021-12-13` и `13 декабря 2021` — последние два можно просто вставить из
документа. Рядом кнопка календаря. Несуществующие даты вроде 31 февраля
подсвечиваются сразу.

Нативное `<input type="date">` здесь не используется намеренно: оно считает
дату готовой после первой же цифры года, что при перерисовке сбрасывало
позицию ввода и не давало дописать год.

## Договоры и залоги

* **Договоры** — каждый договор из отчёта: кредитор, вид займа, «Дата совершения
  сделки», состояние и «Дата фактического прекращения обязательства». Наборы наверху
  (все / действующие / закрытые / новые после сделки / без данных о платежах /
  с залогом) заменили собой три отдельные вкладки: шесть вкладок в ряд читались
  хуже. Редкие поля — плановый срок, основание закрытия, вид участия, агрегат
  отчёта — в строке, которая раскрывается по клику. Плановый срок `31.12.9999`
  (так ОКБ помечает карты без срока) печатается как «бессрочно».
* **Залоги** — раздел «Сведения о залоге» из карточек договоров; вкладка появляется,
  только если залоги в отчёте есть. Названия полей разошлись между версиями отчёта
  (v3: «Дата заключения договора залога», v5: «Дата возникновения залога»), поэтому
  словарь в `parser.js` держит оба написания. Снятым залог считается **только**
  по «Дате фактического прекращения залога»: плановый срок регулярно расходится
  с фактом в обе стороны.

## Инструкция

Кнопка «Инструкция» в шапке (и «Как это работает» на экране загрузки) открывает
встроенное окно с описанием экранов, фильтров, шкалы просрочки и оговорок
о качестве исходных данных. Текст лежит в `src/app.html` (`#help`) и едет
вместе с приложением — отдельного файла, который может отстать от кода, нет.

## Сессии и выгрузка

* **Сохранить сессию** — файл `.json` с разобранным отчётом, датами сделок и
  фильтрами. Открывается мгновенно, без повторного разбора PDF (~30 КБ).
  **Файл сессии содержит персональные данные должника** — храните его там же,
  где материалы дела.
* В `localStorage` сохраняются только настройки фильтров. Персональные данные
  туда не пишутся: на `file://` это хранилище общее для всех локальных страниц.

## Размещение в сети

`dist/index.html` намеренно закоммичен — это позволяет разворачивать сайт без
сборки на стороне хостинга.

Render: **New → Static Site**, подключить репозиторий, Publish Directory —
`dist`, Build Command оставить пустым. Настройки уже описаны в `render.yaml`.

Размещение безопасно: страница полностью клиентская, PDF обрабатывается в
браузере посетителя и на сервер не попадает.

## Старый формат отчёта (до v2)

Отчёты v1.x устроены иначе, и разбор для них отдельный — ветка выбирается по
версии из колонтитула.

* Таблица платежей свёрстана **колонками**: значения идут сверху вниз
  (сумма → основной долг → проценты → иное → дата), причём строки «плавают» —
  у длинных чисел «(%)» переносится на следующую строку. Разбор идёт по
  колонкам, а не по строкам.
* **Статус платежа нарисован иконкой** и в тексте отсутствует. Он читается из
  графического слоя, а соответствие «цвет → статус» берётся из легенды над той
  же таблицей — палитра нигде не зашита.

По умолчанию засчитываются только статусы, при которых деньги поступили
(«Оплачен вовремя», «Оплачен не вовремя» и оба частичных). Остальные видны в
интерфейсе с суммой и отдельной пометкой, набором статусов можно управлять.

«Платёж не наступил» и «Нет данных» помечены одинаково-серым и неразличимы —
они объединены в один статус. Оба означают отсутствие платежа, на расчёт это
не влияет.

## Важно про данные ОКБ

Отчёт содержит два независимых источника цифр по каждому договору:
агрегат «Сумма всех внесенных платежей» и построчную таблицу «Фактические
платежи по договору». Кредиторы передают их отдельно, и **они регулярно не
сходятся**. В проверенном отчёте на 106 страниц расходятся 9 договоров из 10;
в одном случае агрегат равен 0 ₽ при 12 фактических платежах по 5 260 ₽.

Инструмент считает по построчной таблице (это единственный источник дат) и
показывает все расхождения на вкладке «Проверка разбора». Договоры с
расхождением стоит проверять по первичным документам — там список платежей
может быть неполным.

## Оформление

Плиточная раскладка: размер плитки задаёт важность. Цвет несёт смысл, а не
украшает — ирис отмечает период после сделки, шкала «в срок → просрочка свыше
90 дней» показывает платёжную дисциплину месяца, кирпичный означает проблему
с данными. Зелёный нигде не используется как элемент интерфейса, только как
крайняя точка этой шкалы.

Шрифт — **Onest** (SIL Open Font License 1.1), встроен в сборку как data:-URI.
Ссылка на CDN тут не годится: приложение должно работать с флешки без
интернета, и шрифт молча отвалился бы вместе со всей типографикой.

## Разработка

```bash
npm install
node tools/fetch-font.mjs                      # один раз: скачать и встроить Onest
npm run build                                  # пересобрать dist/
node test/run.mjs отчёт1.pdf отчёт2.pdf        # прогнать парсер по реальным PDF
```

`src/fonts/onest.css` в репозиторий не коммитится — его создаёт `fetch-font`.
Без него сборка остановится с понятной ошибкой.

* `src/parser.js` — разбор PDF. Не зависит ни от DOM, ни от файловой системы:
  один и тот же код работает в браузере и в Node-тестах.
* `src/app.html` — интерфейс. Метки `@@PARSER@@`, `@@PDFJS@@`,
  `@@PDFJS_WORKER@@` заменяются при сборке на встроенные скрипты.
* `build.mjs` — сборка в один файл. Экспорты pdf.js вытаскиваются в
  `globalThis` разбором финального `export{...}` бандла, поэтому обновление
  pdf.js не требует правок. `globalThis.pdfjsWorker` заставляет pdf.js
  работать в главном потоке — из `file://` отдельный worker-файл загрузить
  нельзя.
* `test/run.mjs` — сверяет разобранные суммы с контрольными из отчёта.
  Падением считается только сбой разбора (обрыв таблицы, нераспознанная
  сумма); расхождение агрегата со списком — особенность данных ОКБ.
* `test/selftest-build.mjs` — собирает копию приложения со встроенным PDF,
  чтобы прогнать весь путь прямо из `file://`.

Парсер проверен на форматах отчёта **v3.8.2.0** и **v3.19.0.0**.
